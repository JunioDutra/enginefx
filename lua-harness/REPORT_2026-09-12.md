# Evidência do gate Lua/Native Image — 12/09/2026

Resultado após revisão: gate Lua aprovado no JVM e no EXE; prova de plataforma parcial, com áudio nativo ainda bloqueado. O [review do terceiro bloco](../docs/reviews/2026-09-12-lua-native-gate.md) registra reproduções, correções e limites.

| Componente | Versão validada |

| GraalVM | CE `25.3.4.1+1.1`, OpenJDK `25.0.4.1+1` |
| MSVC | `19.44.35228`, x64 |

O plano detalhado fixa Native Build Tools `1.1.12`. O SHA-256 do arquivo GraalVM local foi novamente conferido: `770a0d78aba4c19bd40ee410ec82afbbee8e33fdd762e509006ac64e1007b4ce`.

Na raiz de `enginefx`, usando PowerShell 7+ e toolchain configurado:

```powershell
.\mvnw.cmd -B -f .\lua-harness\pom.xml test
.\lua-harness\verify-native.ps1 -JavaHome C:\caminho\para\graalvm
.\lua-harness\verify-platform-native.ps1 -JavaHome C:\caminho\para\graalvm
```

A execução desta revisão utilizou cache Maven existente em modo offline. O helper confere o release do GraalVM, restaura o ambiente do chamador e limita cada EXE a 30 segundos. O compilador MSVC deve estar disponível para o Native Image. As fixtures STB vêm do próprio repositório; o áudio usa o WAV do checkout irmão DinoFX.

## Resultados revisados

| Verificação | Resultado |
| --- | --- |
| JUnit JVM | 9 testes; zero falhas, erros ou ignorados; build 5,812 s |
| Build Lua Native Image | Sucesso; 1 min 31 s; EXE 18.137.088 bytes |
| Lua no EXE | `callback=84 javaToLua=42 hooks=100 external=true lifecycle=200` |

| Build de plataforma | Sucesso; 1 min 49 s |

Os nove testes também passaram no JDK do GraalVM durante os builds nativos. O EXE Lua é copiado sozinho para um diretório novo em `target/lua-smoke-*`; o módulo UTF-8 com caracteres acentuados é criado ali após a compilação. Nenhuma DLL Lua é copiada para essa pasta. O loader LuaJava extrai `lua5464.dll` dos recursos da imagem.

O EXE executa uma verificação principal e 200 ciclos adicionais de criação/fechamento. A revisão corrigiu o entrypoint anterior, que não chamava a repetição existente apenas no JUnit. Os casos negativos nativos cobrem bytecode, UTF-8 inválido, callback externa ausente, retorno fracionário, loop com `pcall` e loop protegido aninhado. O script exige a mensagem esperada para evitar confundir uma falha de bootstrap com rejeição correta.

## Hook, entrada e capacidades

A leitura é limitada a 1 MiB + 1 byte antes da validação. A callback `engine_record` exige um inteiro sem coerção; o retorno Lua deve ser um número de valor exato. O limite de 100.000 instruções, observado a cada 1.000, vale por estado nesta prova.

`pcall`/`xpcall` mantêm erros ordinários e múltiplos retornos, mas seus wrappers verificam o orçamento antes/depois da chamada e propagam seu esgotamento. O módulo não consegue transformar a exceção do hook em PASS. A falha esperada do loop é conferida especificamente, sem capturar qualquer `Throwable` como evidência de sucesso.

As bibliotecas base, table, string, math e utf8 permanecem disponíveis. A capacidade de aplicação é `engine_record`; `java`, `io`, `os`, `debug`, `package`, `require`, `dofile`, `loadfile`, `load`, `collectgarbage` e os helpers internos são ocultados. O teste também verifica que a callback não expõe `getClass` ao script.

## JNI e DLLs

`resource-config.json` inclui a DLL Lua, as fixtures e as DLLs LWJGL/GLFW/STB. `reachability-metadata.json` mantém as entradas de LuaJava e wrappers Java requeridas pela inicialização JNI; o agent inicial foi usado como ponto de partida, não copiado integralmente. A imagem usa `--enable-native-access=ALL-UNNAMED`. No toolchain fixado 25.3, não há fallback JVM, por isso a opção antiga `--no-fallback` não é passada.

Os bloqueios iniciais de recurso `lua5464.dll` e JNI de `java.lang.Short` foram resolvidos pelos metadados e continuaram resolvidos nesta recompilação. O novo subdiretório `target` está ignorado pelo Git; binários, DLLs, caches e resultados gerados não são fontes versionados.

## Plataforma: alcance e bloqueios

O harness STB decodifica o PNG e inicializa/mensura a fonte. Vulkan é exercitado por `vkEnumerateInstanceVersion`; não há dispositivo, swapchain ou upload de textura. A janela GLFW é oculta e usa `GLFW_NO_API`. O teste invoca o endereço nativo do callback através de JNI/libffi, desfaz a inscrição e libera o callback antes de destruir a janela. Isso substitui a chamada Java direta do harness original; continua sendo entrada sintética, sem tecla física do Windows.

O script copia o EXE de plataforma e a biblioteca `jsound.dll` emitida pelo Native Image para `target/platform-smoke-*`. Após os três marcadores PASS, `AudioSystem.getClip` falha com `java.lang.Error: Can't find java.home ??`, em `JSSecurityManager.loadProperties`. O processo retorna 1; o script preserva esse resultado. Também foi reproduzido o diagnóstico de acesso negado a `jdk.internal.misc.Unsafe`, seguido do fallback `MemoryBackendUnsafeLegacy` e aviso de depreciação.

Áudio nativo não está aprovado. O backend OpenAL planejado, a consolidação do perfil JNI e a prova do renderer completo permanecem nas etapas 12–14, encaminhamento permitido pela etapa 1A. Não foi introduzida dependência de um JDK externo para mascarar a falha do EXE.

## Evidências e limites

Logs locais: `../../.review/bloco3/jvm-before.log`, `regressions-before.log`, `jvm-after.log`, `native-lua.log` e `native-platform.log`. Resultados Surefire e pastas isoladas ficam no `target` do harness. O review e os comandos acima constituem a reprodução versionada.

A prova permite avançar para a API Lua da etapa 1B. Não entrega `ScriptRuntime`, cenas/componentes Lua, migração Nashorn, isolamento completo de mods, limite de memória da VM ou tempo máximo de funções C. Também não comprova ausência de vazamentos, textura/fonte renderizada, pixels, drivers, teclado físico, áudio funcional, CPUs x64 anteriores a v3 ou uma instalação limpa do Windows. Os fontes e testes da engine principal/DinoFX/FarmFX não foram alterados nem reexecutados neste bloco.
